Operations / CI & pre-commit ID

CI & pre-commit

The checker is only useful if it runs where nobody can skip it. But the naive version — scan the whole repo, fail on any finding — turns a legacy repo instantly red and gets the workflow deleted.

The rule: gate the diff, not the repo

# .github/workflows/ironclad.yml
name: ironclad

on: [pull_request]

jobs:
  schema:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: changed schema files only
        run: |
          git diff --name-only --diff-filter=ACMR \
            "origin/${{ github.base_ref }}...HEAD" \
            | grep -E '\.(sql|prisma)$|migrations?/.*\.php$' > changed.txt || true

          if [ ! -s changed.txt ]; then
            echo "no schema files in this PR"
            exit 0
          fi

          python3 scripts/check_schema.py $(cat changed.txt | tr '\n' ' ')

Three things this does that the naive version does not:

  1. Only PRs that touch schema files run the check. A CSS-only PR is not blocked by a schema rule.
  2. Existing debt is not your problem today. Old files stay untouched until someone edits them.
  3. Exit code propagates. No || true on the check itself — only on the grep, which legitimately finds nothing.

Pre-commit, for the fast loop

# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: ironclad
        name: ironclad schema rules
        entry: python3 scripts/check_schema.py
        language: system
        files: '\.(sql|prisma)$|migrations?/.*\.php$'
        pass_filenames: true

This is what actually changes behaviour: the error appears before the commit exists, while the agent still has the context to fix it.

Rolling it out without a mutiny

Week Preset Gate
1 legacy-friendly pre-commit only, warnings, build green
2–3 legacy-friendly CI on changed files, still green
4+ balanced CI blocks on changed files only
later strict when findings are near zero

Do not skip week 1. The point of week 1 is that people see the warnings and learn the rule IDs before anything can block them.

Verifying the gate

A green build proves nothing on its own. Prove it fails when it should:

git checkout -b test-gate
printf 'CREATE TABLE t (status ENUM("a","b"));\n' > broken.sql
git add broken.sql && git commit -m "test: should fail"
git push -u origin test-gate

Open the PR. It must be red, and the red must name DB-01. If it is green, the workflow path or the filter is wrong — not the checker.

What CI should not do

  • Do not scan the whole repo on every PR. Full scans belong in a scheduled job so you can track the count without blocking anyone.
  • Do not || true the checker. That is a decoration, not a gate.
  • Do not gate on strict from day one in a repo that has debt. That is how this tool gets removed.
